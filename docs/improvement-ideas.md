# Идеи по улучшению pg_exporter

Составлено по состоянию на версию 0.6.1. Каждая идея опирается на то, что сейчас есть в коде,
со ссылками на конкретные места. Приоритеты — субъективная оценка соотношения «польза / объём работ».

## Высокий приоритет

### 1. Кэширование результатов скрейпа и защита от параллельных скрейпов — ✅ выполнено

Сейчас каждый `GET /metrics` безусловно запускает `update()` у всех коллекторов
(`src/main.rs:172`). Два Prometheus-сервера, случайный `curl` или уменьшенный `scrape_interval`
умножают нагрузку на базу линейно. Причём тяжёлые коллекторы (`pg_statements`, `pg_tables`,
`pg_indexes` — 800+ строк SQL по всем таблицам) стоят дорого.

Что сделать: минимальный TTL-кэш (`min_scrape_interval_ms` в конфиге) и/или единый «in-flight»
семафор, чтобы конкурентные запросы переиспользовали один набор данных. Данные и так лежат в
`Arc<RwLock<Vec<Row>>>`, то есть `collect()` уже умеет отдавать последний снимок без похода в БД.

Реализовано в ветке `feat/scrape-cache`: `PGEApp::refresh` с single-flight-локом
(конкурентные скрейпы переиспользуют один проход) и TTL-кэшем по `min_scrape_interval_ms`
(по умолчанию `0` — только coalescing). Добавлена метрика `pg_exporter_scrape_cached_total`.

### 2. Таймаут на отдельный запрос, а не только на скрейп целиком

`scrape_timeout_ms` ограничивает скрейп в сумме (`src/main.rs:195`), но одиночный зависший запрос
продолжает жить в пуле: `actix_web::rt::time::timeout` бросает задачи, а не отменяет SQL.
При этом `pool_acquire_timeout_secs` защищает только получение соединения.

Что сделать: выставлять `statement_timeout` на уровне соединения (через `after_connect` в
`PgPoolOptions`, `src/instance/mod.rs:58`) и/или оборачивать каждый `fetch_all` в
`tokio::time::timeout`. Заодно стоит задавать `application_name=pg_exporter` — сейчас экспортёр
не отличим в `pg_stat_activity`, хотя сам же собирает эту вьюху.

### 3. Опрос по расписанию вместо опроса «на запрос»

Развитие идеи 1: фоновая задача обновляет коллекторы с собственным интервалом, а HTTP-хендлер
только рендерит текст. Это разводит латентность скрейпа и латентность БД, делает время ответа
предсказуемым и снимает необходимость в частичных ответах по таймауту
(`src/main.rs:206`). Разные интервалы для дешёвых (`pg_locks`) и дорогих (`pg_statements`)
коллекторов — естественное следствие.

### 4. TLS-соединения с PostgreSQL

`sqlx` подключён без TLS-фич (`Cargo.toml:17`: `postgres`, `runtime-tokio`, `rust_decimal`).
То есть `sslmode=require` в DSN работать не будет, а конфиг допускает любой
`postgres://`-URL (`src/config.rs:116`). Для мониторинга managed-баз это блокер.

Что сделать: добавить `tls-rustls` в фичи sqlx и описать в README поддерживаемые значения
`sslmode`. Если TLS осознанно не нужен — это стоит написать явно, чтобы не выяснять опытным путём.

### 5. Секреты в DSN

Пароль сейчас лежит открытым текстом в `pg_exporter.yml`, а `dsn` попадает в лог при ошибке
подключения (`src/instance/mod.rs:93`). Варианты: поддержка `${ENV_VAR}` внутри DSN, чтение из
файла (`dsn_file`) по аналогии с `*_FILE` в Docker-образах, и маскирование пароля при логировании.

## Средний приоритет

### 6. Точечные тесты вместо поднятия контейнера на каждый тест

Каждый тест в `src/tests/integration.rs` создаёт свой контейнер через
`common::create_test_instance()`. 30+ тестов = 30+ запусков PostgreSQL. Общий контейнер на модуль
(через `OnceCell`/`LazyLock` с раздельными схемами или базами) сократит прогон в разы.

Дополнительно: сейчас нет тестов, которые проверяют версионные ветки SQL на нескольких мажорных
версиях. Матрица по PG 13/15/17 в CI ловила бы регрессии `POSTGRES_V*`-условий, которых не видно
на одном `postgres:17`.

### 7. Разбить крупные коллекторы

`pg_statements.rs` (943 строки), `pg_tables.rs` (839), `pg_activity.rs` (838) сложно менять и
нельзя использовать как образец — в `AGENTS.md` и в skill-файле их прямо помечают как плохие
шаблоны. Вынести регистрацию метрик в отдельный `metrics`-блок или таблицу описаний, отделить SQL
от маппинга. Побочный выигрыш: меньше копипасты `Opts::new(...).namespace(...).const_labels(...)`,
которая повторяется ~сотни раз по коллекторам.

### 8. Гранулярность конфигурации коллекторов

Сейчас есть только `disable_collectors` (список имён). Чего не хватает:
- `enable_collectors` / allow-list для минимальных инсталляций;
- исключение схем и таблиц по шаблону (есть `exclude_db_names`, но нет фильтров по схемам,
  а `pg_tables`/`pg_indexes` ходят по всем пользовательским объектам);
- per-collector интервал, если будет реализована идея 3.

### 9. Метрики о самом экспортёре

Есть `pg_exporter_scrape_duration_seconds`, `..._scrape_errors_total`, `..._pool_size`,
`..._pool_idle` (`src/app.rs:39`). Полезно добавить:
- `pg_exporter_build_info{version, git_hash}` — `version()` в `src/util.rs` уже собирает данные,
  но они видны только в CLI и логах;
- `pg_exporter_collector_enabled{collector}` — чтобы отличать «коллектор выключен» от «данных нет»;
- `pg_exporter_last_scrape_timestamp_seconds{collector}` — детектирует «залипший» снимок данных.

### 10. Alert-правила в комплекте

`monitoring/prometheus/prometheus.yml` содержит только `scrape_configs`, `rule_files` нет.
Готовый набор правил (репликационный лаг, рост `pg_exporter_scrape_errors_total`, приближение к
`max_connections`, возраст транзакций/wraparound, падение `pg_up`) — самая востребованная часть
для пользователя и хорошая проверка того, что нужные метрики вообще экспортируются.

### 11. Health и readiness — разные вещи

`/health` проверяет только `!pool.is_closed()` (`src/main.rs:139`), а пул создаётся лениво
(`connect_lazy`), поэтому «ok» возможен при недоступной базе. README при этом предлагает
использовать один и тот же путь и для liveness, и для readiness. Разумно сделать `/ready`,
опирающийся на `current_cfg().is_some()` и/или успешность последнего скрейпа.

## Низкий приоритет / долгий срок

### 12. Релизная автоматизация

Джоба `build` на тег `v*` собирает бинарь, но никуда его не публикует, а `docker` собирает образ
с `push: false` (`.github/workflows/ci.yml:68`, `:126`). Стоит добавить публикацию GitHub Release
с артефактами, пуш образа в registry и multi-arch сборку (`linux/amd64`, `linux/arm64`).
Заодно по `Dockerfile`: нет кэширования зависимостей (`cargo build --release` идёт сразу после
`COPY ./src`, поэтому любое изменение кода пересобирает весь граф) — `cargo-chef` или отдельный
слой для манифестов заметно ускорит сборку. И `Cargo.lock` не копируется в образ, то есть сборка
идёт по незафиксированным версиям и может отличаться от локальной и от CI.

### 13. Уменьшить размер образа

Финальный слой — `debian:12-slim` плюс `libssl-dev` и `openssl`
(`Dockerfile:15`). Так как TLS у sqlx сейчас не включён, часть этих пакетов может быть не нужна.
Вариант на перспективу: сборка под `musl` и `FROM scratch`/`distroless`, запуск от
непривилегированного пользователя (сейчас контейнер работает под root).

### 14. Конфигурация без перезапуска

`ExporterConfig::load` вызывается только на старте. Перечитывание по `SIGHUP` (или отдельному
эндпоинту) позволило бы добавлять инстансы и менять `disable_collectors` без потери счётчиков.

### 15. Логическая репликация и подписчики

Есть `pg_replication` и `pg_replication_slots`, но нет `pg_stat_subscription` /
`pg_stat_subscription_stats` (PG 15+) и `pg_stat_progress_*` (vacuum, cluster, create index,
basebackup, copy). Это заметный пробел для кластеров с логической репликацией и для наблюдения за
длительными операциями.

### 16. Документированная политика поддерживаемых версий

В `COLLECTOR_INFO` минимальные версии заданы строками («9.5», «16»), а в коде — константами
`POSTGRES_V*`. Значения дублируются и могут разойтись. Один источник истины (константа + функция
форматирования) убрал бы риск. Плюс стоит зафиксировать в README, что происходит на версиях
ниже 9.5: сейчас выводится информационный лог (`src/instance/mod.rs:175`), но коллекторы всё равно
пытаются работать.

### 17. `rust-toolchain.toml`

CI берёт `stable` (`dtolnay/rust-toolchain@stable`), Dockerfile прибит к `rust:1.93-slim`.
Файл `rust-toolchain.toml` синхронизировал бы локальную сборку, CI и образ, а также зафиксировал
минимальную версию для edition 2024.
